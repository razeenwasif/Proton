# Proton code and UX review — 12 September 2026

Proton's strongest architectural choices are its headless Rust core, explicit command/event boundary, isolated workspaces, text-based documents, and staged agent edits. The immediate opportunity is to make the interface consistently honor those choices. Several visible controls still operate as prototype chrome beside the real application.

This review used the current checkout and the running macOS Proton application through computer use. All seven modes, file search by mouse and keyboard, Settings navigation, the Tasks dock, and editor scrolling were inspected. No agent prompts were submitted or document saves performed. Text accidentally routed into the editor during the search test was undone; the original buffer contents and clean tab indicator were verified. The app was returned to Codex with the Agent dock and original scroll position.

## Architecture map

- `crates/proton-shell`: Tauri window, IPC, native backdrop, and a 50 ms poll loop.
- `crates/proton-core`: Session → Workspace → subsystems; modal input, commands/events, mode contracts, and orchestration.
- Supporting Rust crates implement text/undo, indexing, syntax, LSP/DAP, terminals, agents, library retrieval, plugins, and mode-specific documents.
- `ui/app.js`: UI event handlers, rendering, layout, keyboard routing, and all seven modes in approximately 5,900 lines.
- `ui/bridge.js`: Tauri transport plus approximately 1,400 lines of preview behavior and fixtures.
- `ui/bindings`: generated TypeScript definitions. These describe the protocol, but the current JavaScript is not checked against them by a frontend type-check command.

Keep the core/UI separation and the existing subsystem crates. A framework rewrite is unnecessary to address the findings below.

## Prioritized findings

### P1 — Mouse search can modify the code buffer

**Observed:** Clicking the Telescope rail icon displayed an overlay with the demo dashboard preview. Typing `PROGRESS` then closed the overlay, entered replacement mode, and inserted characters into the current C buffer. By contrast, Command-K opened the real picker and correctly returned six matching files.

**Cause:** `ui/index.html:213`, `:289`, and `:866` use `data-open="telescope"`. The generic handler at `ui/app.js:870` only toggles CSS. `pickerOpen` becomes true only in `renderPicker` at `:4249`; the real Command-K path at `:4887` dispatches `openPicker`. The ordinary keyboard handler therefore remains active underneath the mouse-opened overlay.

**Change:** Route every search entry point through one command. Give overlays explicit keyboard ownership and focus, and prevent editor commands while a modal is open. Closing via Escape, scrim, and buttons must update core and view state consistently.

**Acceptance:** Search by icon, Explorer field, Command-K, and leader sequence produces identical behavior. Typing a query never changes a buffer or its dirty flag.

### P1 — Visiting Data can leave Codex drawing only five lines

**Observed:** After visiting Data and returning to Codex, the existing C file rendered just five lines in a full-height editor. Scrolling repopulated the viewport.

**Likely cause supported by source:** `reportEveryViewport` at `ui/app.js:4135` measures all `[data-editor]` elements, including hidden mode surfaces. `reportViewport` at `:4126` converts a zero-height element into five rows, including overscan. Multiple mode surfaces use the same view indices. Data's first split render schedules these measurements, while returning to an existing Codex split does not necessarily schedule fresh measurements.

**Change:** Measure only the visible mode's editor panes; ignore zero-size measurements. Observe actual editor containers and remeasure after each reveal. Wrap the body ResizeObserver callback rather than passing `reportViewport` directly: ResizeObserver supplies entries, while that function expects a numeric view index.

**Acceptance:** Repeated Codex → Data → Codex transitions, split changes, dock resizing, and window resizing preserve a full visible viewport and scroll position.

### P2 — Demo data is presented as current application state

**Observed:** A C file in the Courses workspace showed `orbital-dashboard`, `main +2 ~1`, `tsx`, and `42%`. The Tasks tab showed `2` while the panel said `nothing queued`. Searching for Markdown files still previewed `src/routes/dashboard.tsx`.

**Sources:** `ui/index.html:324`, `:904`, `:938`; `ui/app.js:4320` explicitly preserves the standing preview for non-library pickers. The collaborator avatars at `ui/index.html:200` are also static.

**Change:** Populate metadata and counts exclusively from events. Use neutral empty states until data arrives. Render a real selected-file preview or omit the preview pane. Keep demo fixtures outside the production HTML.

### P2 — Startup assumes Proton's own repository layout

**Observed:** The initial status bar reported that `crates/proton-core/src/vim.rs` did not exist in the active workspace.

**Source:** `boot()` at `ui/app.js:5164` unconditionally opens that path, even in the native application.

**Change:** Restore the workspace's selected buffer or show a welcome surface. Load the example source only in an explicitly enabled preview fixture.

### P2 — Modal navigation and controls lack keyboard semantics

**Observed:** Opening Settings left accessibility focus on the page, and Tab did not move into a Settings control. Settings navigation and Explorer rows appeared as text rather than interactive controls. Search's query is a span, not a text input.

**Sources:** `ui/app.js:4949` onward routes non-editable targets to Vim and suppresses Tab. `ui/index.html:985` lacks dialog semantics; Settings navigation uses clickable divs. `renderTree` at `ui/app.js:1445` creates div rows without tree semantics.

**Change:** Introduce a single input-routing hierarchy: active modal, editable control, terminal, then mode commands. Add focus entry/restoration, contained Tab navigation, accessible names, and semantic buttons/tree items. Follow the [W3C modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

## UI/UX enhancements

1. **Make empty states actionable.** Design: “Open component” / “Open stylesheet.” Data: “Open notebook” / “Create notebook.” Game: “Open Godot project.” Video: “Open EDL.” Modeling: “Create scene” / “Open scene.” State supported file types and capability limits next to the action. Collapse empty inspectors until a selection exists.
2. **Raise text contrast and provide UI scaling.** Labels and guidance are faint at the current window size. `.empty` uses the 22%-opacity `--ink-4` token; on the white Design artboard its message is nearly invisible. Use explicit text/background pairs and target [4.5:1 for ordinary text](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Add comfortable/compact density and a real font-size control.
3. **Give the editor more room.** The two left rails, Explorer, and always-open Agent dock consume much of the width. Add obvious collapse controls and remember widths per mode. At smaller widths, allow one auxiliary panel at a time. Show a readable workspace name near the file context rather than relying on initials.
4. **Make availability visible.** “Build,” “Share,” and the Settings search field look actionable but have no functional wiring in the inspected source. Implement them or remove/disable them with an explanation. Settings also displays Windows backdrop options on macOS; show platform-supported options and the actual applied material.
5. **Shorten Settings copy.** Explain the user's choice first. For example: “Choose the colors used throughout Proton.” Move explanations about tokens, compositor behavior, and implementation details into optional help. Replace display-only control facsimiles with real controls or plain descriptions.
6. **Clarify agent context.** Show the selected workspace, attached files, model/provider readiness, and pending changes before sending. The composer advertises Command-K as inline editing, but Command-K currently opens file search; make the shortcut and label agree.
7. **Group typing into sensible undo steps.** Recovering from the search bug required one undo per inserted character. Group a continuous insert/replace session into one undo transaction, with deliberate boundaries for cursor movement and mode changes.

## Codebase improvements

- **Extract cohesive frontend modules:** keyboard/commands, overlays, editor/splits, picker, settings, agent, and each mode. Preserve the existing DOM and CSS initially. Move preview fixtures into a separate module selected at startup.
- **Actually check the generated contract:** use JSDoc imports with TypeScript `checkJs` and a no-emit CI check, or gradually migrate the boundary to TypeScript. Generating Rust-derived types does not validate JavaScript consumers by itself. [TypeScript documentation](https://www.typescriptlang.org/tsconfig/checkJs.html).
- **Add UI integration tests for the failures above.** Existing Rust tests thoroughly exercise commands, but cannot catch a button dispatching no command or a hidden DOM node reporting the wrong height. Cover click/keyboard parity, modal isolation, Data/Codex transitions, correct metadata, and empty states. Include a native WebView smoke pass.
- **Strengthen event delivery:** `ui/bridge.js:1503` reports IPC failures only to the console. Surface an actionable error in the UI. `Event::Viewport` has a version that its renderer ignores; evaluate workspace/buffer identity and sequence handling for late responses across the reply and push channels. This is a robustness recommendation, not a reproduced ordering failure.
- **Measure end-to-end latency:** the existing latency test measures the core. Add command-to-paint timings and representative large-file/mode-switch cases before changing rendering technology. Avoid logging entire events and document contents for every command in ordinary debug sessions.
- **Refresh architecture documentation:** `docs/ARCHITECTURE.md` describes Modeling/Game/Video as a plan and cites 609 tests; README describes implemented document support and cites 1,333. Publish one current capability matrix and generate test totals where useful.
- **Make path tests portable and run a platform matrix:** six core unit tests fail on macOS in `crates/proton-core/src/folder.rs`. Temporary-directory tests append Windows backslashes, and others assume Windows `PathBuf` interpretation. Use native path construction for filesystem tests and separate platform-specific lexical tests. These failures do not by themselves establish that ordinary macOS folder opening is broken.

## Suggested implementation sequence

1. Fix search dispatch, modal keyboard ownership, and viewport measurement; add regression coverage.
2. Remove production demo state and the hardcoded boot file; correct metadata, previews, and task counts.
3. Improve contrast, mode onboarding, panel collapse, and platform-specific Settings.
4. Extract frontend modules and introduce protocol type checking incrementally.

## Implemented first batch

Following approval, the first implementation batch addresses the reproduced search and viewport failures, removes misleading production fixtures, and improves the surrounding controls:

- Mouse and keyboard search share the core command path. Search uses a native text input, including paste, and closing the overlay cancels core picker state. Folder queries still support Tab completion.
- Settings and search own focus and keyboard input, keep the background inert, and restore focus on dismissal. Overlay lifecycle is extracted into `ui/overlays.js`.
- Visible editor panes are measured after mode changes and resizing; hidden panes cannot shrink the core viewport.
- Selecting a file now updates the active split and paints the chosen buffer immediately. Notebook selection uses the notebook loader; mode-specific stylesheet, scene, and EDL selection uses the corresponding loader. Grep retains exact source-line navigation.
- Native startup preserves restored buffers. Workspace, branch, file type, position, and task count come from events. The fake transcript, collaborator avatars, file preview, and misleading composer shortcut are removed.
- Empty states have clearer text and file-opening actions. Build and Share explain their unavailable state, Settings uses semantic navigation buttons, and macOS shows Vibrancy/Solid background choices.
- Window chrome and the macOS vibrancy layer use matching 13 px rounded corners. Choosing Solid clears native vibrancy.
- Transport failures produce a visible notice.
